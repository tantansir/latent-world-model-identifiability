# What Can Latent World Models Know?

**Physical Parameter Identifiability in Multimodal Predictive Representations**

Code and results for a controlled study of *which* physical
quantities a prediction-trained latent actually contains, and *what decides* it.
The [project page](https://tantansir.github.io/latent-world-model-identifiability/)
carries video demonstrations that the static figures cannot.

---

## The short version

A latent world model is usually justified by the claim that predicting the
future forces a representation to internalize physics. We test that claim under
interventions instead of assuming it.

Every result passes a **certificate gate**: a parameter must first be *certified
recoverable* from raw observations before any statement about a model is made,
so a null result can be attributed to the objective rather than to the
environment or the probe. Under that gate:

- **Inputs bound what can be known; prediction targets decide what is
  retained.** Contact stiffness enters the latent only when touch is
  *forecast* (R² 0.50), not when the same signal is merely fused into the
  input (−0.02).
- **Single-step vision-only models sit in a lazy equilibrium**, discarding even
  perfectly visible object state (position R² 0.04).
- **The map has a frontier.** Drag carries a recoverability certificate of 0.89
  yet plateaus near 0.13 under every deterministic prediction objective we
  test, while a supervised head on the same trunk reaches 0.45. Parameters whose
  readout is slow *and* ratio-type under the sensed coordinates fall outside
  what these objectives acquire.
- **On RH20T** (two robots, 4,258 episodes) the same mechanisms govern real
  streams: every arm missing information or prediction pressure stays flat over
  a 5× data range.

## Repository layout

| Path | What is in it |
| --- | --- |
| `exp/e001_xmodal_jepa/` | **PokeWorld** simulator (`pokeworld.py`), the X-JEPA model, and the input × target factorial |
| `exp/e002_multiscale/` | Multi-horizon prediction heads (Δ ∈ {1, 4, 16}) |
| `exp/e003_motion/` | Motion channel, flow sensor, λ sweep, attribute-matrix constructions, CEM planning |
| `exp/e005_patchtok/` | Patch-token architecture variant |
| `exp/e010_rh20t/` | Real-robot pipeline: RH20T preprocessing, training, evaluation, joint cross-embodiment training |
| `docs/` | Project page, its video assets, and the scripts that generate them |

Every `results/*.json` in `exp/` is a completed run: probe R², certificates,
rollout and direct-Δ error, and the real-data readouts. The paper's tables and
figures are generated from these files.

## Reproducing

The whole study — including all real-robot experiments — was run on a single
RTX 4060. Models are ~5M parameters and train in under an hour each.

```bash
# 1. PokeWorld: generate data and run the input x target factorial
cd exp/e001_xmodal_jepa && python run_e001.py

# 2. Multi-horizon heads, motion channel, and the lambda sweep
cd exp/e003_motion && python train.py --variant VFX --seed 0 --lam 0.02

# 3. Closed-loop planning on the frozen latent
cd exp/e003_motion && python plan_eval.py VFX_s0_l0.005 viz

# 4. Real robot (RH20T): preprocess, then train
cd exp/e010_rh20t
python prep.py observation.images.cam_035622060973 data_cfg1 <path-to-cfg1>
E010_DATA=data_cfg1 python train.py --variant VFX --seed 0
```

Two caveats worth knowing before you run anything. Paths inside the scripts are
absolute and point at the machine the study was run on — edit them, or set the
environment variables the scripts read. And the preprocessed corpora and
checkpoints (about 80 GB) are not in this repository; `prep.py` regenerates the
real-robot side from the public dataset, and the PokeWorld side is generated by
the simulator itself.

The real-robot data is [RH20T](https://rh20t.github.io/); this work uses
configurations 1 (Flexiv) and 7 (KUKA).
